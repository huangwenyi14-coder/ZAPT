# Physical Record 三字段精确定位契约

更新日期：2026-07-16

适用范围：EvidenceForge Record Index、Record Ground Truth、黄金检测器输出和
record-level 评测

## 1. 目的

本文档统一说明检测器如何引用一条最终物理日志，以及评测器如何确认预测确实
指向正确文件中的正确记录。

检测器必须使用以下三个字段提交一条 record-level 预测：

```text
physical_record_id + relative_path + record_index
```

这三个字段分别承担“全局记录主键”“所属日志文件”和“文件内记录序号”三种
职责。评测器不会仅凭时间、PID、IP、Zeek UID 或日志文本猜测预测位置。

## 2. 三个字段的含义

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `physical_record_id` | 当前数据集发布中一条最终原子物理记录的唯一主键 | `pr-aca24f29b25d20680e90fe94` |
| `relative_path` | 相对于场景 `data/` 根目录的 POSIX 路径 | `DC-PMC-01.pacific-mapping.local/ecar.json` |
| `record_index` | 该文件内从 `0` 开始计算的原子记录序号 | `410` |

### 2.1 physical_record_id

`physical_record_id` 是评测查找 Ground Truth 的主键。它绑定当前数据集、文件
相对路径、记录序号和最终记录内容哈希。

它不能反向解码出文件路径或记录内容，也不能替代另外两个定位字段。检测器必须
从无标签的 `RECORD_INDEX.jsonl` 读取并原样返回，不得自行构造。

### 2.2 relative_path

`relative_path` 表示记录所在的日志文件，其根目录是当前场景的 `data/`：

```text
<scenario-output>/data/<relative_path>
```

示例：

```text
<scenario-output>/data/DC-PMC-01.pacific-mapping.local/ecar.json
```

路径必须是安全的相对路径，不能是绝对路径，也不能包含 `..` 跳转。

### 2.3 record_index

`record_index` 是文件内的原子记录序号，从 `0` 开始：

```text
第 1 条记录  -> record_index = 0
第 2 条记录  -> record_index = 1
第 411 条记录 -> record_index = 410
```

它是“记录序号”，不应无条件理解成文本编辑器中的行号。

| 日志组织方式 | `record_index` 的含义 | 与文本行号的关系 |
| --- | --- | --- |
| JSONL、Zeek JSON、单行文本日志 | 第几个 JSON/日志记录 | 通常为 `文本行号 - 1` |
| JSON 数组 | 数组中的元素下标 | 与文本行号无固定关系 |
| Windows XML Event 流 | 第几个 `<Event>` 记录 | 一个 Event 可能跨多行 |
| 多行 Bash history 或多行记录 | 解析后的原子记录序号 | 与文本行号无固定关系 |

因此，“`record_index = 410` 就是第 411 行”只适用于一行一记录的文件。

## 3. 完整实例

黄金检测器输出一条恶意预测：

```json
{
  "physical_record_id": "pr-aca24f29b25d20680e90fe94",
  "relative_path": "DC-PMC-01.pacific-mapping.local/ecar.json",
  "record_index": 410,
  "label": "malicious",
  "confidence": 0.985,
  "reason": "same five-tuple and time as pr-e7f572f9bd75d68386b995c2"
}
```

私有 `RECORD_GROUND_TRUTH.jsonl` 中对应记录为：

```json
{
  "physical_record_id": "pr-aca24f29b25d20680e90fe94",
  "relative_path": "DC-PMC-01.pacific-mapping.local/ecar.json",
  "record_index": 410,
  "byte_offset": 156388,
  "byte_length": 329,
  "record_sha256": "ff14fbea441df27c694b116c60f82045e480e04fa3823e1010073d69b5988bed",
  "label": "malicious",
  "logical_event_id": "le-9a0e9e7d426fb0a1745b3930",
  "storyline_id": "baxia-002-curl-delivery",
  "event_type": "connection",
  "source_format": "ecar"
}
```

实际文件定位为：

```text
<scenario-output>/data/DC-PMC-01.pacific-mapping.local/ecar.json
```

该文件是一行一条记录的 JSONL，因此 `record_index = 410` 对应文件中的第
411 行。其内容为：

```json
{
  "timestamp_ms": 1721871498435,
  "id": "c8526f86-30ee-4676-ae9a-b76646ea7bef",
  "hostname": "DC-PMC-01",
  "object": "FLOW",
  "action": "CONNECT",
  "objectID": "2a572f41-94d1-47a6-960a-8d241b93bcd5",
  "tid": 16084,
  "properties": {
    "src_ip": "10.84.30.20",
    "src_port": "65470",
    "dst_ip": "10.84.20.10",
    "dst_port": "53",
    "protocol": "udp",
    "direction": "INBOUND"
  }
}
```

该行原始字节的 SHA-256 与 Ground Truth 中的 `record_sha256` 完全一致。

## 4. 评测器的精确匹配流程

评测器按以下顺序处理每条超过置信度阈值的预测：

```text
读取 prediction.physical_record_id
  -> 在私有 RECORD_GROUND_TRUTH 中按主键查找
  -> 校验 prediction.relative_path == truth.relative_path
  -> 校验 prediction.record_index == truth.record_index
  -> 定位有效后读取私有 label
  -> malicious 为 TP，benign/red_herring 为 FP
```

具体判定如下：

| 情况 | 评测结果 |
| --- | --- |
| ID 存在，路径和 index 一致，Ground Truth 为 malicious | TP |
| ID 存在，路径和 index 一致，Ground Truth 为 benign/red_herring | FP |
| `physical_record_id` 不存在 | 无效引用，计入 FP |
| ID 存在，但 `relative_path` 或 `record_index` 不一致 | locator mismatch，计入 FP |
| Ground Truth 为 malicious，但没有有效预测 | FN |

这意味着只猜对 `physical_record_id` 但填写错误位置，不能获得有效命中；只填写
正确路径和 index 但缺少真实 `physical_record_id`，也不能获得有效命中。

## 5. 三字段与审计字段的分工

三字段用于评测定位：

```text
physical_record_id
relative_path
record_index
```

以下字段用于更严格的字节级审计：

```text
byte_offset
byte_length
record_sha256
```

| 字段 | 作用 |
| --- | --- |
| `byte_offset` | 原子记录在最终文件中的起始字节位置 |
| `byte_length` | 原子记录占用的字节数 |
| `record_sha256` | 对最终原子记录字节计算的完整 SHA-256 |

审计时可以读取：

```text
data/relative_path[byte_offset : byte_offset + byte_length]
```

再计算 SHA-256，并与 `record_sha256` 比较。这样即使记录是多行 XML 或其他
复杂格式，也能证明定位到的确实是生成 Ground Truth 时的同一条记录。

## 6. Blind 数据与私有 Ground Truth 的边界

检测器可以看到无标签 `RECORD_INDEX.jsonl` 中的定位字段：

```text
physical_record_id
relative_path
record_index
byte_offset
byte_length
record_sha256
公开 correlation_features
```

检测器不能看到以下私有字段：

```text
label
storyline_id
logical_event_id
provenance_kind
detectability_class
```

因此，检测器返回 `physical_record_id` 不等于获得了标签。它仍然必须根据源日志
内容和公开关联特征判断哪些物理记录属于恶意活动。

## 7. 实现与使用要求

### 检测器

1. 从 `RECORD_INDEX.jsonl` 原样读取三个定位字段；
2. 不要根据行号自行生成 `physical_record_id`；
3. 返回预测时同时携带三个字段；
4. 不要把 PID、时间戳、Zeek UID 或日志文本哈希当作全局主键；
5. `reason`、`confidence` 和关联强度用于解释预测，但不替代精确定位字段。

### 评测器

1. 首先按 `physical_record_id` 查私有 Ground Truth；
2. 必须继续校验 `relative_path` 和 `record_index`；
3. 对未知 ID 和 locator mismatch 分别记录审计原因；
4. 在需要验证数据完整性时，重新计算 `record_sha256`；
5. 只有三字段校验通过后，才能把预测聚合到 `logical_event_id` 和
   `storyline_id` 层面。

### 数据生成与发布

1. `record_index` 必须基于最终输出文件，而不是 emitter 的临时缓冲顺序；
2. finalizer 对日志重排或重写后，必须重新计算 index、offset、length 和 hash；
3. 同一数据集内不允许重复 `physical_record_id`；
4. 同一文件内不允许重复 `(relative_path, record_index)` 定位器；
5. 日志内容、路径或前置记录发生变化时，应重新生成定位 sidecar。

## 8. 一句话定义

```text
physical_record_id 回答“是哪条记录”；
relative_path 回答“在哪个日志文件”；
record_index 回答“是该文件中的第几个原子记录”。
```

三者共同构成 record-level 检测输出的精确定位契约。
