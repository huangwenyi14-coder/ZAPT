# 威胁报告到数据集的端到端质量治理设计

**日期：** 2026-08-26
**状态：** 已获用户确认，待制定实施计划
**适用范围：** TXT/可复制文字 PDF 到 EvidenceForge 标准数据集
**前置设计：** [2026-08-26-report-to-dataset-design.md](2026-08-26-report-to-dataset-design.md)

## 1. 背景与结论

现有报告导入链路已经能完成文本提取、MiniMax 结构化抽取、场景转换和确定性
日志生成，但对 APT-C-48 报告的对齐审计表明，“成功生成”不等于“忠实生成”。
主要失真包括：

- 报告未提及 PowerShell，却被转换器选为恶意进程的最终默认值；
- `cmd.exe` 只负责打开诱饵 PDF，却因“上一进程”兜底成为后续下载、持久化和 C2
  通信的所有者；
- 战役级网络字段整体合并，导致诱饵下载 URI 被继承到上线通信；
- 单值持久化结构无法完整表达两个计划任务；
- 注册表查询等原项目不支持的行为可能被误物化为注册表写入；
- 现有质量门主要统计步骤数、阶段数和 ATT&CK 覆盖率，不检查来源关系是否正确。

这些问题横跨模型抽取、中间数据契约、场景编译器、EvidenceForge 事件能力和验收测试。
因此，只调整提示词或在生成 JSON 前多调用两次 MiniMax 无法根治。本设计将质量所有权
分配到正确的层，建立“来源事实→受控补全→语义编译→日志物化→反向核对”闭环。

## 2. 目标与非目标

### 2.1 目标

1. 用户只执行一次命令，内部可执行有限的抽取、审核、补全和修复。
2. 报告明确事实必须完整保留，精确值和事实关系不得被后续转换改写。
3. 允许 AI 为生成数据补齐必要字段，但每个补全字段都必须可识别、可追溯、不与来源冲突。
4. 场景编译以显式实体和关系为输入，禁止使用“上一进程”和“整体战役网络字典”
   等高风险语义兜底。
5. 短 TXT 按其真实信息量生成小而连贯的场景，不再为满足固定步骤数而补造攻击阶段。
6. 完整 PDF 对可物化来源行为的覆盖率不低于 90%，关键语义错误为零。
7. 最终仍交付 EvidenceForge 标准输出，不交付原文抽取、模型原始响应或内部结构化
   JSON。

### 2.2 非目标

- 不支持 OCR 扫描 PDF、Word、网页或图片输入；
- 不在本轮建设 Web 界面或 HTTP API；
- 不保证每项报告行为都能在当前采集源中直接可见；
- 不为了报告还原而重写 EvidenceForge 的整个确定性生成引擎；
- 不将新闻站点、报告发布页或厂商链接提升为攻击基础设施。

## 3. 质量原则

### 3.1 可以补全，不能冒充来源

数据分为四类字段来源：

| 来源 | 含义 | 例子 |
|---|---|---|
| `source` | 报告明确披露 | 域名、URL、计划任务名、命令行 |
| `derived` | 可由来源值确定性推导 | HTTPS URL 的 443 端口、URL 的 URI |
| `ai_completed` | 为物化已知行为而补全 | 未知恶意进程本地路径、邮件收件人 |
| `engine_generated` | 由 EvidenceForge 运行时产生 | PID、源端口、时间抖动、会话 ID |

步骤层再汇总为“报告事实”“部分 AI 补全”或“完全仿真”。

### 3.2 补字段，不补无关攻击故事

AI 可以补充已知行为的必要参数和技术前置，不得新增报告没有描述的独立攻击阶段。
例如，报告明确说明“下载并执行”时可补充本地保存路径，但不能因为该攻击“通常会”
偷取凭据就新增凭据窃取步骤。

### 3.3 不可观测不等于不重要

每项事实编译前分类为：

- `native`：原项目可以正确生成；
- `approximated`：可以合理近似，必须记录近似方式；
- `ground_truth_only`：当前数据源不能合理观测，只保留在 Ground Truth。

不得为了增加日志数量，把 `ground_truth_only` 事实伪造成另一种事件。

## 4. 端到端架构

```text
TXT / 带文本层 PDF
        |
        v
带页码和字符位置的文档片段
        |
        +------> 确定性 IOC 与精确值候选
        |
        v
MiniMax A：来源事实账本
        |
        v
本地来源与关系校验
        |
        v
MiniMax B：完整性与关系审核
        |
        v
MiniMax C：受控仿真补全计划
        |
        v
报告专用语义编译器
        |
        v
生成前来源质量门
        |
        v
eforge validate + 确定性生成
        |
        v
最终恶意记录反向核对
        |
        v
EvidenceForge 标准输出
```

用户只发起一次生成。A、B、C 是职责独立的内部模型任务，不是对同一 JSON 无限改写。

## 5. 中间数据契约

### 5.1 来源引用

文本提取器为每个可引用片段生成：

- `span_id`；
- PDF 页码或 TXT 段落序号；
- 全文字符起止位置；
- 规范化文本的摘要哈希；
- 受限长度的引用文本，仅用于内部校验。

模型宣称的每个 `source` 字段必须引用至少一个 `span_id`。精确 IOC、路径、命令、计划任务名
和注册表键必须能在所引用片段中找到，不能只因为它出现在报告其他位置就通过。

### 5.2 事实、实体和关系

`ReportFactLedger` 至少包含：

- `facts`：原子化行为，包含稳定 `fact_id`、行为类型、顺序、引用和不确定性；
- `entities`：进程、文件、URL、网络端点、计划任务、注册表对象、邮件；
- `relations`：事实与实体、实体与实体的有向关系；
- `report_iocs`：报告级 IOC 与其来源位置；
- `source_metadata`：报告名、组织、行业等元数据。

所有可重复实体都使用列表，不得将多个任务名、进程名或 URL 拼接到一个单值字段。

### 5.3 仿真计划

`SimulationPlan` 只能补充已存在的事实或必要技术前置，并为每个补全字段记录：

- 目标事实/实体 ID；
- 字段路径；
- 补全值；
- 补全理由；
- 与来源事实的兼容性判断；
- 补全类型 `derived` 或 `ai_completed`。

## 6. MiniMax 任务分工

### 6.1 A：事实抽取

只回答“报告说了什么”，不生成场景节点，不选择 EvidenceForge 事件类型，不为满足阶段数填充行为。
每项事实必须附来源引用，ATT&CK 仅作为可选的保守映射。

### 6.2 B：完整性审核

输入原报告与第一次事实账本，只输出：

- 遗漏候选；
- 重复事实；
- 精确值与行为错绑；
- 事实顺序矛盾；
- 应拆分的复合事实；
- 无法获得来源支持的字段。

审核器不直接改写账本。本地代码只接受通过引用校验的修正。

### 6.3 C：受控补全

只处理编译器列出的缺失字段，不重新解读报告。可补充用户、主机、本地路径、邮件字段、合理
时序和显式推导的 HTTP 方法。不得补充报告级 IOC、样本哈希、新的攻击行为、漏洞、恶意软件名称
或精确命令。

### 6.4 调用边界

- 每个任务使用独立提示词版本和强制工具 Schema；
- 抽取或审核的结构失败最多定向修复一次；
- 确定性来源错误、编译错误和日志物化错误不通过额外模型调用掩盖；
- 默认温度使用接口支持的最低稳定值；
- 模型调用数、版本和质量指标可记录，提示词和原始响应不发布。

## 7. AI 补全政策

### 7.1 允许

- 受害用户名、主机名、企业内网 IP；
- 报告未披露名称的恶意进程的本地仿真路径；
- 报告明确描述下载但未给出的本地落地路径；
- 仿真邮件的收发件人、主题和内部邮件服务器；
- 运行时时间、进程父子关系和会话前置；
- 报告明确行为必需的 DNS、登录、文件落地等技术前置。

### 7.2 可确定性推导

- HTTPS 默认 443；
- 完整 URL 拆分域名与 URI；
- 明确“下载”可使用 GET，明确“上传/回传”可使用 POST；
- 明确指定周期的计划任务可编译为对应任务 XML；
- 自删除未给出路径时，可删除同一恶意进程实体的 AI 补全映像路径。

### 7.3 禁止

- 报告未出现的攻击域名、IP、URL 和报告样本哈希；
- 把来源 URL 绑定到报告未明确关联的另一行为；
- 把未知恶意进程默认为 PowerShell、CMD、WScript 或其他具体解释器；
- 伪造报告精确命令行、漏洞编号、恶意软件名或时间；
- 新增报告没有描述的凭据窃取、横向移动等独立攻击阶段；
- 把 `ai_completed` 或 `engine_generated` 标记为报告来源事实。

## 8. 报告专用场景编译器

新编译器位于 `src/evidenceforge/report_ingest/`，不再将通用的
`scripts/regenerate_apt_scenarios.py` 当作报告导入的黑盒。可将环境、人员、主机、时间窗口等可复用
部分抽取为正式库模块，但报告事实到事件的映射使用新契约。

### 8.1 强制编译规则

1. 每个进程都有稳定实体 ID 和 `process_ref`。
2. 网络、文件、注册表、计划任务等进程所有行为必须显式引用所有者。
3. 不允许用主机的上一进程填充所有者；缺少时创建带来源标记的 AI 补全恶意进程。
4. 同一网络端点只可复用域名、IP、端口和明确的协议。
5. URI、HTTP 方法、上传/下载方向、文件名和内容含义必须绑定到当前事实，不可从战役级
   上下文继承。
6. 一个计划任务实体生成一个 `scheduled_task_created`。
7. 报告描述的邮件投递使用 `email_message`，不使用 Outlook 进程代替邮件证据。
8. 无法合理可观测的事实进入 `ground_truth_only`，不为了物化而修改行为语义。

### 8.2 旧转换器安全收紧

`regenerate_apt_scenarios.py` 仍保留给原 APT JSON 批量转换流程，但需移除三项通用危险行为：

- Windows 进程的 PowerShell 最终默认值；
- 将完整战役网络字典合并到每一步；
- 将主机的“上一进程”默认设为后续攻击行为所有者。

这些收紧必须用现有 APT 转换回归测试保护。

## 9. EvidenceForge 能力改动

### 9.1 直接复用

- `email_message`、`process`、`connection`、`dns_query`；
- `file_create`、`file_delete`、`file_collection`；
- `scheduled_task_created`、`service_installed`；
- `process_access`、`image_load`；
- 现有多源日志、Gold Label 和记录级 Ground Truth。

### 9.2 新增 `registry_query`

注册表查询不能使用 `registry_set` 近似。新增最小型原生事件：

- 场景模型包含 `process_ref`、`key`和可选 `value_name`；
- 规范事件的 RegistryContext 使用 `read` 动作；
- eCAR/EDR 输出 `REGISTRY/READ`；
- Sysmon 不输出 12/13，因为这些是注册表创建/写入证据；
- Ground Truth 记录该行为只在部分日志源可见。

eCAR 格式已支持 `READ` 动作，不需要重写格式模板，主要改动位于事件模型、Storyline
执行器、eCAR 渲染器和 Ground Truth 模型。

### 9.3 来源元数据

Storyline 步骤增加可选的来源元数据：

- 步骤来源分类；
- 对应事实 ID；
- 来源页码/段落；
- AI 补全字段路径；
- 可观测分类与降级理由。

该元数据进入 `GROUND_TRUTH.md/json`，不渲染到安全日志。`GROUND_TRUTH.md` 增加中文
“来源与仿真说明”，`GROUND_TRUTH.json` 保留机器可读分类。不保留完整报告原文或模型响应。

## 10. 质量门

### 10.1 生成前硬门槛

| 指标 | 要求 |
|---|---:|
| 报告精确值的来源引用验证率 | 100% |
| AI/引擎补全字段标记率 | 100% |
| 报告级 IOC 在 Ground Truth 中的保留率 | 100% |
| 不受支持的进程、命令、URL 关系 | 0 |
| 可物化来源行为覆盖率 | ≥ 90% |
| 未记录原因的降级事实 | 0 |
| 来源贴合综合分 | ≥ 85 |

任一关键硬门槛失败时，综合分再高也不允许发布。

### 10.2 建议评分构成

- 来源事实准确性：30%；
- 来源行为覆盖：25%；
- 实体与关系正确性：20%；
- IOC 保留与绑定正确性：15%；
- 场景到最终日志的物化完整性：10%。

评分基于报告事实数量和关系数量，不要求固定步骤数、固定攻击阶段数或高 ATT&CK 覆盖率。

### 10.3 生成后反向核对

通过 `RECORD_GROUND_TRUTH.jsonl` 定位恶意物理记录，并验证：

1. 每个 `native` 事件至少产生一条预期物理证据；
2. `ground_truth_only` 事实不伪造物理记录；
3. 已编译的进程、网络、文件和任务关系与事实账本一致；
4. TLS 中不可见的 URL 标记为“来源存在、当前日志不可见”，不按日志缺失误判；
5. Ground Truth、Gold Label 和记录级标签引用相同的 Storyline ID；
6. 最终攻击记录中不存在未标记的模型精确声称。

## 11. 错误归属与修复策略

| 错误类型 | 所有层 | 修复方式 |
|---|---|---|
| 来源事实遗漏 | 抽取 Schema/提示词 | 审核请求补抽并执行引用校验 |
| 精确值错绑 | 事实关系层 | 拒绝错误关系，定向重建该关系 |
| 无来源字段 | 来源校验层 | 删除或改为明确 AI 补全，不静默接受 |
| 场景步骤丢失/类型错误 | 报告编译器 | 修编译器并增加回归测试，不让模型改口 |
| 日志物化不正确 | EvidenceForge 事件/生成层 | 修事件所有层，不在单个渲染器打补丁 |
| 数据源无法观测 | 可观测能力矩阵 | 降级为 `ground_truth_only` 或增加真实可观测事件 |

线上一次命令内只对模型所有的抽取/审核错误进行有限修复。编译器和生成器缺陷必须在开发中根治，
不得通过运行时反复请求模型规避。

## 12. 测试与循环迭代

### 12.1 确定性单元测试

- 两个计划任务编译为两个事件；
- 未知恶意进程不得变成 PowerShell；
- 下载 URL 不得串到上线通信；
- `cmd.exe` 只负责它被明确绑定的诱饵文件打开行为；
- 注册表查询不产生注册表写入；
- 每个 AI 字段都有标记和理由；
- 每个来源精确值都可验证其引用位置；
- 短报告不因少于 5 步或 3 个阶段而失败。

### 12.2 APT-C-48 语义回归矩阵

必须出现：

- 3 个 MD5、4 个攻击 URL、`panbaiclu.com` 和 `158.255.215.248`；
- `SCS-Update` 和 `User_Feed_Synchronization` 两个计划任务及各自路径；
- `C:\Windows\System32\cmd.exe /c` 打开诱饵文档；
- 诱饵文档与后续组件两类下载；
- 用户名、进程列表和模块列表回传事实；
- BIOS 注册表查询、反分析判断和自删除事实。

禁止出现：

- 报告未提及的 PowerShell 攻击主线；
- `cmd.exe` 拥有后续 C2、下载和计划任务行为；
- `/Guide/Architecture.pdf` 被当作上线包 URI；
- 注册表查询被渲染为注册表写入；
- 未标记来源的精确进程、URL、命令和 IOC。

### 12.3 小型端到端数据集

开发循环使用缩短时间窗口和低强度基线，只通过记录级 Ground Truth 定位恶意证据，检查场景到
物理记录的语义一致性。确定性测试全部通过后，再运行完整数据集生成。

### 12.4 真实 MiniMax 稳定性验收

1. APT-C-48 PDF 从空目录独立运行 3 次；
2. 每次用户只执行一次命令，中间不手工修改场景；
3. 3 次均满足硬门槛且来源贴合分不低于 85；
4. 再使用至少三类独立 TXT：
   - 极简、无 IOC 的行为描述；
   - 只有网络 IOC 和 C2 行为的报告；
   - 包含多个任务、文件或 URL 的报告；
5. 每类均从空目录一轮生成通过；
6. 保存评分、版本和失败分类，不保存密钥和模型原始响应。

每次失败先添加可重现回归测试，再修正所有层。禁止增加仅对 APT-C-48 文件名、组织名或
特定 IOC 生效的样例补丁。

## 14. 兼容性与发布

- 现有手写场景不需要添加来源元数据；
- `registry_query` 是新的可选事件类型；
- 现有日志格式不改变已有记录语义；
- Ground Truth Schema 增加来源字段时必须更新 schema version，加载器对旧版仍保持兼容；
- 报告专用编译器上线后，报告导入命令不再经过旧的启发式事件路由；
- 实施期每完成一组逻辑修改建立独立中文 Git 提交，不 amend 已有提交。

## 15. 完成定义

实施仅在同时满足以下条件时完成：

1. APT-C-48 PDF 连续 3 次从空目录一轮生成通过；
2. 三类独立 TXT 一轮生成通过；
3. 各次来源贴合分均不低于 85；
4. 关键语义错误为零，可物化来源行为覆盖率不低于 90%；
5. 报告级 IOC 在 Ground Truth 中 100% 保留；
6. AI 和引擎补全字段 100% 标记；
7. 完整场景通过 `eforge validate`；
8. 完整数据集生成成功，并通过记录级反向核对；
9. 项目既有默认测试无回归，新增/修改文件通过 Ruff；
10. 最终结果不需要人工修改 `scenario.yaml`。
